# 按拍同步 → 按帧渲染：通用插值方法（根治"线抽抽 / 框抽抽"）

> 本文件是这一项的**唯一权威记录**：根因、通用件、用到哪些地方、判据、验证约定。
> 起因：用户反复报"牵引枪的线抽抽、牵引的地方的框也抽抽"，并明确要求
> **"我们不能弄个通用方法来解决这个问题吗"** —— 也就是不要再打补丁。

## 一、根因：这条 bug 类不是牵引枪独有的

老写法是 `lerp(prev, cur, partialTick)`。它有一个**没写出来、但必须成立**的前提：

> `prev ← cur; cur ← 新值` 这次交换**恰好发生在 tick 边界**（partialTick = 0）。

只有那样，两段折线才首尾相接：

```
交换前 φ→1：lerp = P(t)
交换后 φ=0 ：lerp = P(t)      ← 接上了
```

而现实里，**数据是按"拍"到的、帧是在任意相位渲染的**，于是交换落在一个任意相位 φ₀：

```
交换前：P(t−1) + φ₀·Δ
交换后：P(t)   + φ₀·Δ = 交换前 + Δ        ← 每个采样周期凭空跳一整个 Δ
```

注意跳变幅度 = **Δ**（与 φ₀ 无关）⇒ 表现就是"动一下 → 停一下 → 又跳一下"。**采样越稀，Δ 越大，越难看。**

### 1.1 这个类已经害过我们两次

| 时间 | 症状 | Δ 有多大 | 修法 |
|---|---|---|---|
| 2026-09-25 | 天体移动"还是不丝滑" | 地球每 tick **108 km** ⇒ 站在 2.2R 处看 ≈ **6.9 像素**（而顺滑运动每帧才 2.3 像素） | `CelestialBody` 改成**带时间戳的快照环 + 渲染延迟** |
| 2026-10-02 | 牵引枪**线抽抽、框也抽抽** | 端点是服务端广播来的，`BROADCAST_INTERVAL_TICKS = 2` ⇒ **10Hz**，而插值窗口只有 1 tick | 抽成通用件 `TimedSamples`，牵引枪接上 |

**牵引枪那两条症状是同一个源**：框的中心就是同一个 `renderEnd` 的输出——
```java
b.renderEnd(partialTick, E);        // 画线用它
...
lockCenter = E;                     // 框也用它
```
所以以前"分开修线、分开修框"必然修不好：它们是同一个数。

## 二、通用件

### 2.1 `com.mss.polymech.util.TimedSamples`

把 `CelestialBody` 里那份**已验证过**的机制抽出来（本项目硬规矩：同一概念不许有两份实现）：

- 每拍 `push(value...)` 打一个 `System.nanoTime()` 时间戳；
- 渲染取 `渲染时刻 = 现在 − 延迟`，在**包住这个时刻的相邻两拍**之间插值；
- **越过最新样本一律夹住，绝不外推**（外推会在丢包时把物体甩到屏幕外）；
- 同一拍去重窗口 4 ms（上游一次逻辑更新可能分几次调用）；
- 四元数走 **slerp + 最短弧**（分量线性插值在四元数上是错的；短弧不做会绕一大圈
  —— 本项目在牵引枪角伺服上栽过同一个坑）。

### 2.2 ★ 延迟必须"由发包间隔推出"，不能照抄

这是本次最容易踩的坑，也是把关系写成**式子**而不是注释的原因：

```java
// PhysgunClientState
private static final double INTERP_DELAY_SECONDS =
        2.0 * PhysgunBeamPacket.BROADCAST_INTERVAL_TICKS / 20.0;
```

延迟必须 **≥ 2 × 采样周期**，"渲染时刻永远被两拍包住"才成立：

| 场景 | 采样节奏 | 默认 0.10 s 够吗 |
|---|---|---|
| 天体 | **每帧**推进（100+ Hz） | 够，余量好几拍 |
| 牵引枪（原 `INTERVAL=2`） | 每 2 tick = **0.1 s** | **不够**：延迟刚好 = 1 个周期 ⇒ 网络稍抖就越过最新样本、被夹住不动 ⇒ **又开始抽** |

所以同时把发包间隔也改了：

```java
// PhysgunBeamPacket
public static final int BROADCAST_INTERVAL_TICKS = 1;   // 原 2
```

两个理由：① 采样越稀每拍跳变越大；② 它决定渲染延迟 —— 间隔 0.05 s ⇒ 延迟 0.10 s，
**与天空那条线取的是同一个数**（`CelestialBody.INTERP_DELAY_SECONDS = 0.10`）。

## 三、用到了哪里

| 渲染量 | 之前 | 现在 |
|---|---|---|
| 光束**起点**（射手枪口） | `lerp(prevStart, start, partialTick)` | `startSamples.evaluate` |
| 光束**终点** ← 线 + 框的共同来源 | `lerp(prevEnd, end, partialTick)` | **不再插值网络值**：改成「抓点 + 客户端体位姿」每帧现算（见 §六）；位姿消费走 `renderTransform`（见 §七） |
| **虚拟竿尖**（受力弯曲） | `lerp(tipPrev, tip, partialTick)` | `tipSamples.evaluate` |
| 抓取框/悬停框的体位姿 | `poseOf` → `liveTransform` 直读 | ⚠️ **原断言已证伪**：直读是 10ms 阶梯（§七）。现走 `renderTransform` |
| 方块（物理体本体）渲染 | `liveTransform` 直读 | 同上 —— 方块/框/光束终点**必须同口径**，否则互相错开 |
| 兜底位姿（镜子不在本地物理世界时） | `ClientBody.render*`（4 条环） | 2 条网络环（`net*`，延迟 2×50ms）；`phys*` 四条环是**从未接线的死代码**，已删（§七） |

三处都保留**旧的 `lerp` 作为回退**：样本不足（刚抓上，还没攒够两拍）时最多抽一两拍，
而不是因为样本没攒够就整条光束不动。

## 四、判据（程序判定，不让用户肉眼说"好像不抽了"）

### 4.1 游戏内：`[牵引枪·丝滑判据]`

`com.mss.polymech.util.FrameJitterMeter`（同为通用件）在渲染时逐帧喂**光束终点 E**，
窗口按**时间**开（1.2 秒，与帧率无关），**松手那一刻**打一行（照 `[牵引枪·旋转判据]` 的做法，不刷屏）：

```
[牵引枪·丝滑判据] 1.2 秒 674 帧：逐帧速度 均=1.482 最大=1.553 最小=1.401 格/秒；
    抖动(最大/均)=1.05（阈值 1.50）；停帧=0/673 ⇒ PASS
```

> **v2（2026-10-04）两处口径修正**（各有事故背书，见 §七）：
> ① 统计的是**逐帧速度**（位移 ÷ 帧间隔），不是裸位移 —— 帧间隔不均时裸位移两头误报
> （GC 卡帧虚高、高帧率步进短帧漏判）；
> ② 窗口按**时间**开 —— v1 的"120 帧"在 60fps 是 2 秒、560fps 只有 0.21 秒，
> 同一个判据在不同机器上量的不是同一段时间。读数里打印的是**实际观察时长**。
> "跳变帧"随之改称**停帧**（速度 < 5% 均值 —— 语义就是"上游在动而这一帧没动"）。

口径与天空那条线的"太空顺滑"**同源**（每帧量、抖动 = 最大/均），避免同一种毛病两套说法。

⚠️ **均值≈0 时判"不可判"而不是 PASS**：物体本来就没动（例如抓着一个躺在地上的体），
"没动"与"动得丝滑"是两件事 —— 判 PASS 就是一条永远通过的**假判据**（本项目栽过"死判据"）。

### 4.2 实机判据表（绝对坐标；程序判定 PASS/FAIL）

| # | 操作 | 判据 | 期望 |
|---|---|---|---|
| S1 | 抓一个物体，**横向走动** 1~2 秒后松手 | 聊天栏出现 `[牵引枪·丝滑判据]` | PASS = 抖动 ≤ 1.50 且 **停帧 = 0** |
| S2 | 抓一个物体，**原地快速甩视角** 1~2 秒后松手 | 同上 | PASS = 抖动 ≤ 1.50 且 停帧 = 0（甩视角时速度变化最大，最容易暴露） |
| S3 | 抓着一个**正在飞的**物体（推进/爆炸后） | 同上 | PASS = 抖动 ≤ 1.50；这条的动态最猛，是三条里最严的 |
| S4 | 抓着物体**转它**（TAB + 鼠标） | 线跟着转、框**不跳格** | PASS = 框始终套在同一格上，不来回蹦 |
| S5 | 抓一个**静止**的物体不动，然后松手 | 读数应说"静默样本…不可判" | PASS = **不出现 PASS**（这条验的是判据本身不是死的） |

### 4.3 离线：第 19 步 `InterpSmoothnessProbe`（6/6，已落地）

**调的是生产代码本体**（`TimedSamples` / `FrameJitterMeter`），不是复刻一份公式 ——
本项目栽过"探针复刻的契约与真实现不一致"。时钟由 `TimedSamples` 的**可注入构造器**给定，
所以"任意相位"是**确定性**的（靠 `Thread.sleep` 造相位不行：Windows 粒度约 15ms，而一个 tick 才 50ms）。

仿真：200fps 渲染 + 20Hz 采样（= 改完后的 `BROADCAST_INTERVAL_TICKS = 1`）+ 延迟 2 个采样周期 + 匀速 8 格/秒。

| 组 | 场景 | 实测 | 结论 |
|---|---|---|---|
| **A** | **固定相位**（交换正好在 tick 边界）+ 旧 lerp | 均=0.0400 最大=0.0400 抖动=**1.00** | PASS —— 证明**量具本身能给出 PASS** |
| **B** | ★ **任意相位**（半个采样周期）+ 旧 lerp | 均=0.1120 最小=0.0400 最大=0.4400 抖动=**3.93** | **如期 FAIL** —— 判据不是死的，这就是"抽抽"的量化 |
| **C** | 同样的任意相位 + `TimedSamples` | 均=0.0400 最大=0.0400 抖动=**1.00** | PASS —— 修好了 |
| **D** | 连续丢 4 拍 + `TimedSamples` | 最大越界 **0.000000e+00** 格；丢包后仍在插值 | PASS —— **夹住，不外推**，也没被冻死 |

★ **没有 A 与 B，C 的 PASS 就是死判据**：A 证明量具能通过、B 证明量具能失败。

**B 组暴露的"抽"是锯齿，不是停顿**：每帧位移最小 0.04（= 一帧的真实位移）、最大 0.44（≈ 11 帧的量）。
机理是旧写法在交换那一刻**倒退**到新一拍的值（本次探针里那一段的 partial 从 0.9 掉回 0），
所以 `跳变帧`（位移 < 5% 均值）为 0 而 `抖动`=3.93 —— **判这个毛病要看抖动，不是看跳变帧**；
`跳变帧` 抓的是另一种失效（夹住后冻死）。

⚠️ **本探针第一版把自己判 FAIL 过一次，原因是判据写错**：用 `simTime % samplePeriod` 算 `partialTick`，
浮点取模在 tick 边界给出 `0.0499999` 而不是 `0`，于是 `partialTick≈1` 下一帧又跳回 `0.1`，
**凭空造出一个倒退跳变**（A 组因此冤枉地抖动 4.15）。改成整数帧运算后 A 组 = 1.00。
教训与 §5.3（`-q90`）、`BodyLocalMappingProbe` C 组同源：**期望写错时先怀疑判据，不要先怀疑代码**。
已用契约钉住那个整数写法。

### 4.4 天体那份私有实现已收口（第 20 步 `CelestialSmoothProbe`）

机制抽出来之后，`CelestialBody` 里那份**私有实现**（`histT/histP/histR` + `locate`）必须改为委托 ——
否则"同一概念两份实现"迟早漂移（本项目硬规矩）。

但那是**已经验收过的天空那条线**，而此前**没有任何离线探针覆盖它**：改完只能靠人去游戏里
看天空有没有变卡，那正是用户明确说过不想反复做的事。所以顺序是**先钉住、再重构**：

| | 抖动 | 每帧位移 | 不外推 | 单位四元数 | 转角步长 |
|---|---|---|---|---|---|
| **重构前** | 1.00 | 0.1500 | 47.8499 ≤ 50.2500 | 4.44e-16 | 0.00508 |
| **重构后** | 1.01 | **0.1500** | 47.8495 ≤ 50.2500 | 2.22e-16 | 0.00506 |

差异只在末位，且来自探针用**忙等**推进真实时间（类内部时钟是 `System.nanoTime()`，
**没有**可注入时钟 ⇒ 不能用 `sleep`：Windows 粒度约 15ms，而一帧才 5ms）。
**每帧位移 0.1500 完全一致** = 速度没被拉慢/加快，这是"行为没变"最硬的一条。

探针的 5 条判据：① 平滑（抖动 ≤ 1.5 且 跳变帧 = 0）② 每帧位移量级（期待 速度/帧率）
③ 不外推 ④ 姿态恒为单位四元数 ⑤ 转角步长有界（最短弧没坏）。

**唯一有意保留的语义差异**：原来位置与姿态被绑成**同一拍**（两条环共用一个时间戳），
现在各一条环、各按自己的节奏插值 —— 姿态更新稀疏时不会再被位置拖着走。语义上更准。

收口后 `TimedSamples` 是全项目**唯一**一份"带时间戳的插值"实现，使用方：
`PhysgunClientState`（3 条环）、`ClientPhysicsWorld.ClientBody`（4 条环）、`CelestialBody`（2 条环）。

1. `.\gradlew compileJava --console=plain` 必须 `BUILD SUCCESSFUL`。
2. `.\native\jni-smoketest\run-offline-checks.ps1` 必须 **22/22 步、exit 0**。
3. **任何**"按拍同步、按帧渲染"的新量都必须走 `TimedSamples`，不许再写
   `lerp(prev, cur, partialTick)` —— 契约钉住了 `PhysgunClientState` 里那一处；
   新增同类渲染量时请照抄它的接法（谁写数据谁 `push`，读的时候 `evaluate`）。
4. **延迟必须由采样周期推出**：新增一处时先问"这个量多久来一拍"，
   然后 `delay = 2 × 周期`。契约钉的就是这条式子（`2.0 * BROADCAST_INTERVAL_TICKS / 20.0`）。
5. 改了发包间隔 ⇒ 延迟自动跟着变，但**采样越稀越难看**，别为了省包把它调大。
6. 助手不启动客户端；实机由用户验。

## 六、★ 端点的**数据模型**才是根因（2026-10-03 改）：抓点，不是世界坐标

§一~§五 做的是"把 20Hz 的世界点插得更顺"。那**治标**：用户实机反馈
**"玩家不动时没有抽搐了，但玩家一动又有了"** —— 而"不动时好"什么都没证明：
物体静止时 Δ=0，任何插值都不可能抽。

### 6.1 真正的根因

世界坐标是**派生量**：`world = 体位姿 · 抓点`。把它当成一等公民在网络上发，必然有两个后果：

1. **混叠**：服务端只能按自己的 tick 采样体位姿 ⇒ 发出去的是 **20Hz 的世界点**；
   而物体被拖着在地面上走时，接触解算的抖动是 **100Hz** 量级
   （`mps-clone-plan` 第 22 节那条已记录、已拍板"接受"的穿透锯齿）。
   **20Hz 采样 100Hz = 混叠** ⇒ 玩家一动就抽；不动时物体静止 ⇒ 不抽。
2. **延迟**：客户端再插值这些世界点就必须付 ≥2 拍（100ms）的渲染延迟。

### 6.2 参考怎么做的（这就是"通用方法"的答案）

Create Aeronautics 的 `physics_staff` 存的是**体局部抓点**：

```java
// PhysicsStaffClientHandler:134 / :239   收发的是局部抓点，不是世界点
final Vec3 hitLocation = JOMLConversion.toMojang(this.dragSession.dragLocalAnchor);
// :374-384  渲染时用**客户端自己的**位姿逐帧变换
Vec3 interpolatedBeamEnd = beam.previousEnd.lerp(beam.end, pt);
interpolatedBeamEnd = subLevel.renderPose(pt).transformPosition(interpolatedBeamEnd);
```

`previousEnd.lerp(end, pt)` 插的是局部抓点 —— 抓着的时候它是**常量**，所以那个 lerp 是空操作，
**不存在相位问题**。所有运动都在 `renderPose(pt)` 里，而它是逐帧求值的
⇒ 世界点从**连续量**现算，结构上不可能混叠，也不需要延迟。

### 6.3 本项目的改法（面向对象，不是打补丁）

新增 `com.mss.polymech.physics.BodyLocalAnchor`（`bodyId` + 体局部 xyz）：

| 层 | 之前（面向结果） | 现在（面向对象） |
|---|---|---|
| 包 `PhysgunBeamPacket` | `startX/Y/Z + endX/Y/Z`（世界点） | `bodyId + localX/Y/Z`（**抓点本体**） |
| 服务端 `broadcast` | 每个 tick 采样体位姿算世界点 | 直接发 `Grab` 里那个常量抓点（并删掉死代码 `worldAnchor`） |
| 客户端预测 | 预测一组世界端点 | 预测一个 `BodyLocalAnchor`（`PhysgunTarget.Hit` 本来就有 `localX/Y/Z`） |
| 客户端渲染 | 插值世界点（`endSamples`） | `refreshEnd()` 每帧用**客户端自己的**位姿派生（`liveTransform` → 兜底 `ClientBody.render*`） |

**换算只有一处**：`BodyLocalAnchor.toWorld(...)` —— 服务端、预测、渲染共用，三边不可能各算一套。

**副作用（好的）**：那 100ms 渲染延迟**不用付了**；`renderEnd` 现在返回 `boolean`，
客户端还没同步到那个体时**这一帧不画**（而不是拿旧世界点硬画，看着像"光束钉在原地"）。

`TimedSamples` 仍然保留 —— 但只给**真正的**拍同步量用（起点＝服务端广播、竿尖＝客户端 tick 的弹簧状态）。
**终点不再需要它**：那正是"用插值补偿一个错误的数据模型"。

### 6.4 实机判据（补 §4.2）

| # | 操作 | 判据 | 期望 |
|---|---|---|---|
| S6 | 抓一个物体，**拖着它在地面上走**（这正是原来必抽的场景） | `[牵引枪·丝滑判据]` | PASS = 抖动 ≤ 1.50 且 **停帧 = 0**（对照：改之前玩家一动必抽） |
| S7 | 拖着物体走时看**框** | 框应一直套在同一格上 | PASS = 不来回跳格 |
| S8 | 抓住一个体后**立刻**看（镜子体还没同步到） | 那一两帧**不画**这条光束，随后出现 | PASS = 不出现"钉在原点/上一位置"的错误光束 |

**mustNot**：`double endX, double endY, double endZ,`（世界端点不得回归）。

### 7.2 归因（三步，全部程序判定）

1. **算术对表**：零位移帧占比理论值 = `1 − 100/fps`。560fps ⇒ 82%，实测 101/120 = 84%；
   19 个爆发帧 ≈ 120/5.6 ≈ 每 5.6 帧一个 100Hz 物理步；爆发帧位移 ≈ 速度/100 × fps。
   三个数全部对上 ⇒ 这是**"直读 10ms 阶梯"的指纹**。量级本身是平滑的（每步 1.6~2.25cm）。
2. **代码归因**：`refreshEnd` / `poseOf`（框）/ 方块渲染的首选都是
   `ClientPhysics.liveTransform` —— 直读运动学镜像的**步进后瞬时状态**（held 零阶保持）。
   而文档断言"100Hz 本地刚体状态本来就平滑，无需插值"所依赖的 `captureShipTransforms`
   + `ClientBody.phys*` 四条环 —— **从未被任何代码调用**（`physValid` 恒 false）。
   写了不接线 = 没有；死架子比没有架子更误导人（它让错误的断言看起来有依据）。
3. **离线复现（第 19 步 E/F 组）**：同一条匀速直线，只改消费方式 ——
   - **E 直读阶梯 @600fps**：`停帧=850/1019（83%）、抖动=6.03 ⇒ 如期 FAIL`
     —— 与实机（84%、8.12）同形；
   - **F 同一信号过 `TimedSamples`（延迟 2×10ms）**：`停帧=0、抖动=1.20 ⇒ PASS`；
   - **E/F 平均速度一致**（7.961 vs 8.000）⇒ 两组量的是同一条运动，
     差异只可能来自消费方式。**归因闭环。**

   部分周期只走 4/5 步）⇒ 周期性 10ms 停顿。

2. **信号地板 ≈2.3：服务端弹簧是 20Hz 脉冲。** 每 MC tick 打一次冲量 = 方波激励 ⇒

   **修**：施力下到**步进线程的 100Hz 子步**（`PhysgunItem.physicsStep`，
   `J = F×0.01`，频率×5 单次÷5，**平均力与限幅手感逐位不变**；CA 的等价物是求解器内连续 motor，
   我们原生只有冲量 API，按子步摊是同一件事）。`Grab` 由 record 改 class（volatile 伺服快照，

   ——静止窗口的零位移是天经地义（枪口那 91% 全是水分），**速度尖峰仍由抖动抓**。

没画出来就不画标记（不拿上一帧的旧 S 凑数）。契约：`must` ahead 公式 + `mustNot getEyePosition`。

**玩家框**：修复（实体插值基准 + 兄弟差分）已在 §7.9 落地并过 22/22 —— 用户这轮的"还是抽搐 +
位置不对"**大概率是没重启到含框修复的构建**（框修复与线终点修复不在同一批编译里）。
若重启后仍不对，要一张第三人称截图再判（可能是姿态/中心偏移口径，而不是消费路径）。

### 7.11 第六轮：玩家框二修（黄点 ✓，框仍不行 ⇒ 上一轮"没重启"的猜测是错的）

用户复测：**黄点好了**（§7.10 的修复生效，说明跑的是含框修复的最新构建）；**玩家框仍不行**，
且明确点出"第二/三人称下**位置**有问题"。⇒ 上一轮"大概率没重启"的猜测**被证伪**，框的修复本身有漏。

**根因两条（读 `SpaceBodyTiltMixin` 与 `SpacePlayerData` 后定死）**：

1. **姿态没乘 —— "位置不对"的真身**。第三人称玩家模型走 `SpaceBodyTiltMixin`：
   绕 `pivot = bodyCenterOffset` 旋转、乘 `bodyQuatForRender(pt)`（slerp 平滑）、
   超人姿态再叠 `Rx(+SUPERMAN_PRONE_PITCH_DEG)` 趴平。而框是**轴对齐、不带任何姿态**的
   —— 模型一转（滚转 / 超人飞行）框不转，视觉上就是"框不在人身上"。
   （space 的 `PhysicalPlayerColliderRender` 是乘 `body.getRotation()` 的 —— 它带姿态，
   我们连姿态都没有，这一步比参考还缺。）
2. **兄弟差分是子步噪声 —— "抽搐"的真身**。上一版保留的 `rawSibling − rawMain`：
   `PlayerPhysicsBody.afterStep` **每个子步**都写 `sibling.pos = main.pos`，
   帧级读到的只是"主刚体已积分、兄弟还没重合"的**子步中间态**，每帧都不同
   ⇒ 兄弟橙框相对主框抽动。那点"被带走时的错开"只在子步内部存在，帧级渲染根本显示不出来
   —— 它不是信息，是噪声。

**修法五条（与模型逐项对齐）**：① 位置基准 = 实体插值 `lerp(xo, x, pt)`（不变）；
② 中心偏移改取 **`rig.centerOffset()`**（建体时锁死、姿态切换同步更新的值，不是每帧重算）；
③ **乘 `bodyQuatForRender(pt)`**（slerp 平滑的渲染姿态，与模型同一个来源；
用物理真实姿态会暴露 100Hz 采样率 —— `SpacePlayerData` 注释里已踩过这个坑）；
④ 超人姿态叠 `Rx(+90)`（与模型的"趴平"一致）；⑤ **丢弃兄弟差分**，两盒同一基准。

**契约**：`must` 实体插值基准 / `bodyQuatForRender` / `rig.centerOffset()`；
`mustNot` `rig.readPosition(`（框不得再直读刚体）+ `rawSibling[0] - rawMain[0]`（差分不得回归）。

**复测**：F3 + 第三人称，走动/滚转/超人飞行三种姿态下框都应贴着人、姿态跟着人转、不抽。

### 7.12 第七轮：**根因是 pt 取错了** —— `getGameTimeDeltaTicks()` 不是部分刻（2026-10-05）

用户复测（§7.11 之后）：**框仍然随移动抽搐，且第二/三人称下位置不对**。

§7.11 已经把框的**基准/姿态/支点**逐项对齐到模型（实体插值基准、`bodyQuatForRender`、
`rig.centerOffset()`），代码上这三项确实与 `SpaceBodyTiltMixin` 逐项相同 —— 所以这一轮不再猜姿态，
改成**反汇编运行时字节码**核对"喂进去的 pt 到底是什么"。

#### 决定性证据（`build/moddev/artifacts/neoforge-21.1.228-merged.jar` → `DeltaTracker$Timer`）

```text
public float getGameTimeDeltaTicks();          // 0: getfield deltaTicks  → freturn
public float getGameTimeDeltaPartialTick(Z);   // → deltaTickResidual（或 pausedDeltaTickResidual）
```

而 `advanceGameTime(long)` 里两者的来源完全不同：

```text
deltaTicks        = (now - lastMs) / targetMspt        // 本帧步长 ≈ 0.02~0.08（500fps）
deltaTickResidual += deltaTicks;                       // 累积
deltaTickResidual -= (int) deltaTickResidual;          // 余量 ∈ [0,1) ← 这才是部分刻
```

**结论**：`getGameTimeDeltaTicks()` 是"这一帧走了多少刻"，**不是**插值系数；
原版实体渲染用的是 `getGameTimeDeltaPartialTick(...)`（`LevelRenderer.renderEntity` →
`Mth.lerp(pt, entity.xOld, entity.getX())`，pt 来自 `DeltaTracker.getGameTimeDeltaPartialTick`）。

#### 症状为什么正好是这两条

`PlayerColliderRender` 用的是 `Mth.lerp(pt, player.xo, player.getX())`。把 pt 从"0~1 扫过整刻"
换成"≈0.04 的本帧步长"：

1. **抽搐**：`lerp(0.04, xo, x)` ≈ `xo` = **上一刻的位置**。渲染位置只在 tick 边界才变
   ⇒ 20Hz 台阶（而模型用真 pt，是平滑的）—— 两者相对运动，看着就是框在抽。
2. **第二/三人称位置不对**：框比人**慢一整刻**（10 m/s 时约 0.5 格）。第一人称框在相机里看不见，
   切到第二/三人称立刻暴露。

#### 影响面（同一概念两份实现 —— 这才是它藏了这么久的原因）

| 位置 | 原来取的 | 判定 |
| --- | --- | --- |
| `PlayerColliderRender:91` | `getGameTimeDeltaTicks()` | ❌ 框 |
| `PhysgunBeamRenderer:190` | `getGameTimeDeltaTicks()` | ❌ 线/枪口（§7.5 判据一直 FAIL 的"停帧"来源） |
| `PhysicsBodyRenderer:79` | `getGameTimeDeltaTicks()` | ❌ 物理体方块 |
| `SpaceRenderer:153` | `getGameTimeDeltaTicks()` | ❌ 天体 |
| `PhysgunTarget:47` | `getGameTimeDeltaPartialTick(false)` | ✅ 本来就对 |
| `ClientPhysics:129` | `getGameTimeDeltaPartialTick(false)` | ✅ 本来就对 |

**同一概念、两份实现**：瞄准/物理那一路取对了（所以"黄点/射线"一直没问题），
渲染那一路取错了（所以"框/线/枪口"一直抽）。这也解释了 §7.4~§7.11 所有"改了还是抽"的复测
—— 那几轮改的都是**消费方式**，而喂进去的系数本身就是错的。

#### 修法（结构，不是补丁）

新增 `com.mss.polymech.util.PartialTicks`，把"部分刻怎么取"收敛成**唯一实现**：
`of(DeltaTracker)` 为核心，另有 `of(RenderLevelStageEvent)` 与 `level()` 两个入口；
上表六处全部改为经它取。契约（`native/jni-smoketest/check-artifact.ps1`）新增：
`must` `PartialTicks`、`mustNot` `getGameTimeDeltaTicks`。

#### 复测（F3，太空）

1. 走动/滚转时框**贴着人**、不再落后半格、不再台阶跳；
2. 第二/三人称下框与人重合（第一人称看不见是正常的）；
3. 牵引枪读数：`[牵引枪·丝滑判据]` 的"抖动/停帧"应显著下降（枪口尤其明显 —— 它直接由 pt 驱动）。

#### 这次不再靠人眼：`[玩家框·丝滑判据]`

框"抽搐/位置不对"被连报三轮、前两轮只能靠人眼复述症状，结论来回摇摆。所以这一轮顺手把
**框自己也接上了通用件**（`FrameJitterMeter`）：`PlayerColliderRender` 每帧按**绝对世界坐标**
采样框中心，攒够 1.2 秒就程序判定 —— 日志记一行，聊天栏只在 PASS/FAIL **翻转**时打一次
（避免每 1.2 秒刷屏）。

- 站着不动 ⇒ 报"不可判"（速度均值≈0，判据不许自欺，见 `FrameJitterMeter` 契约）；
- 走起来 ⇒ 一行 `[玩家框·丝滑判据] … 抖动(最大/均)=x.xx（阈值 1.50）；停帧=n/m ⇒ PASS/FAIL`。

**这条判据与相机无关**（量的是世界坐标），所以它同时覆盖第一/二/三人称 —— 正是"别让用户
替我们解释天文/几何数据"的那条规矩。

### 7.13 第八轮：**位置不对的根因是渲染阶段**（模型坐标全对，flush 时矩阵是错的）

用户复测（§7.12 之后）：**抽搐好了**（"现在是没抽抽了"），但**框在第几人称下位置都不对**。
并明确指出方法问题："一个方法长时间没修好，你得看看是不是路子出问题了"。

#### 先让程序说话（§7.12 埋的自检）

```
[框·插值自检] pt(框)=0.4800 pt(模型)=0.4800 pt(相机)=0.4800
              | xo=… x=… xOld=… | 两侧基准差=0.0000 格 ⇒ PASS（框与模型同源）
[玩家框·丝滑判据] 与 [模型基准·丝滑判据] 两条读数**逐位相同**
```

⇒ **框的位姿数据与模型完全同源**（同 pt、同插值基准、同中心偏移、同姿态四元数）。
既然数据一模一样却画在不同地方，问题只可能出在"**画到屏幕上的那一步**"。

#### 根因：`AFTER_SOLID_BLOCKS` 触发时，相机矩阵还没压栈

反汇编/阅读运行时 `LevelRenderer`（`build/moddev/artifacts/neoforge-21.1.228-merged.jar` 与
NeoForge sources）的时间线：

```text
:972   renderSectionLayer(RenderType.solid())   ← AFTER_SOLID_BLOCKS 在这里发出
:974   renderSectionLayer(cutoutMipped())
:976   renderSectionLayer(cutout())
:1001  matrix4fstack = RenderSystem.getModelViewStack()
:1002  matrix4fstack.pushMatrix().mul(frustumMatrix)   ← 相机矩阵【才在这里】压栈
:1009  实体循环（玩家模型在这里画，modelView = frustumMatrix ✓）
:1052  dispatchRenderStage(AFTER_ENTITIES)              ← 同一个矩阵框 ✓
:1184  renderSectionLayer(translucent)                  ← AFTER_TRANSLUCENT_BLOCKS ✓
:1242  matrix4fstack.popMatrix()
```

两条硬事实（都是运行时字节码/源码，不是推断）：

1. **`poseStack` 里没有相机旋转**。带 RenderType 的阶段由 `ClientHooks.dispatchRenderStage(RenderType,…)`
   发出，那条重载**传的 poseStack 是 `null`**；事件类替我们 `new PoseStack()`（单位矩阵）。
   相机旋转只在 **modelView 矩阵**里 —— 而 flush 时着色器读的是
   `RenderSystem.getModelViewStack()` 的栈顶。
2. **`AFTER_SOLID_BLOCKS` 的栈顶不是相机矩阵**（`:1002` 才压）。地形看不出来是因为 chunk shader
   直接把 `frustumMatrix` 喂给 uniform；实体也看不出来是因为它们在压栈之后才画。
   **只有"在压栈之前 flush 的自定义线框"会画歪** —— 全项目只有玩家框踩在这个阶段。

⇒ 症状完全吻合：**框的绝对世界坐标正确**（自检 PASS），但屏幕位置随相机姿态乱漂，
"第几人称都不对"，第一人称满屏大线（相机在盒子里、又被错位矩阵放大）。
文件里那句"只有 `event.getPoseStack()` 带着相机旋转"的旧注释是**错的**，已订正。

#### 修法（两条，都是构造性保证）

1. 阶段改 **`AFTER_ENTITIES`**：与玩家模型在**同一个 modelView 帧**里 flush
   （`AFTER_SOLID_BLOCKS` 全项目唯一回退，`mustNot` 已钉死）。
2. flush 前**显式**把 modelView 设成 `event.getModelViewMatrix()`（= `frustumMatrix`），
   `try/finally` 里 pop —— 不再依赖任何阶段"碰巧"留下的栈状态
   （与 `SpaceRenderer` 画天体时 push/set/pop 的纪律一致）。

**契约**：`must Stage.AFTER_ENTITIES` / `event.getModelViewMatrix()`；
`mustNot AFTER_SOLID_BLOCKS`。

#### 新增自检（万一还不对，日志能直接算出落点）

```
[框·坐标系] cam=(cx,cy,cz) 框中心=(mx,my,mz) Δ(相机-框)=(dx,dy,dz)
            | 自然modelView对角=(m00,m11,m22,m33)
```
`自然modelView对角≈(1,1,1,1)` 即单位矩阵，就是"框在没有相机旋转的矩阵里画"的直接证据。

### 7.14 第九轮：**第一人称的相机锚在世界竖直，而身体是 6DOF 的**

用户复测（§7.13 之后）：**第二/三人称对了**（"其他人称的对了"），但**第一人称仍异常**：
"F3 下随便移动一下视角，框的位置就会有些异常"。

#### 读数（程序判的）

```
[框·坐标系] Δ(相机-框)=(0.000, 0.720, 0.000)     ← 相机在框正上方 0.72，且方向是【世界 +Y】
            cam=(1395410.811,1082.227,-14713824.051)
            框中心=(1395410.811,1081.507,-14713824.051)
（同一时刻 HUD：俯仰 −88° / 滚转 −180° —— 身体基本是倒着的）
```

`0.72 = 眼高 1.62 − 中心偏移 0.90` —— 数值对，但**方向是世界竖直**。

#### 根因：第一人称走了原版锚点

- **第二/三人称**：`SpaceCameraMixin.polymech$headAnchor` 把相机锚在
  **身体坐标系**的眼睛：`实体位置 + (0, 支点, 0) + Q_body·(0, 眼高 − 支点, 0)` ✓ —— 所以那边复测已经对了。
- **第一人称**：那个方法的守卫里有 `!this.isDetached()`，第一人称**直接放行给原版**，
  于是锚点是 `lerp(pt, yo, y) + 眼高` —— **世界竖直**方向。

太空里身体是 6DOF 的（实测 俯仰 −88°/滚转 −180°），"头上的那一点"**并不在世界 +Y**。
⇒ 第一人称的眼睛被钉在身体**另一侧**；身体一转，眼睛与身体的相对关系就变
⇒ 画在身体中心 + 身体姿态上的碰撞框看着"位置异常"，随便转视角更明显。

（第一人称下玩家模型不渲染，所以 `pt(模型)` 那一项是**陈旧值** —— 日志里 0.98 与 0.92 的差
不是真错位，是 `SpaceBodyTiltMixin` 没机会刷新。）

#### 修法

去掉 `polymech$headAnchor` 守卫里的 `!this.isDetached()`：**第一、二、三人称一律走身体锚点**
（非太空维度 / 非玩家仍走原版）。

**契约**：`mustNot '!this.isDetached() ||'`（SpaceCameraMixin）。

#### 复测（F3）

1. 第一人称：框应当"裹着你"且**随视角稳定**（不再一转视角就漂）；
2. 二/三人称：保持 §7.13 的结果（框压在人身上）；
3. 极端姿态（滚转 ±180°、俯仰 ±90°）下重复 1/2。

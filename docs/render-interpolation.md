# 按拍同步 → 按帧渲染：通用插值方法（根治"线抽抽 / 框抽抽"）

> 本文件是这一项的**唯一权威记录**：根因、通用件、用到哪些地方、判据、验证约定。
> 起因：用户反复报"牵引枪的线抽抽、牵引的地方的框也抽抽"，并明确要求
> **"我们不能弄个通用方法来解决这个问题吗"** —— 也就是不要再打补丁。

## 一、根因：这条 bug 类不是牵引枪独有的

老写法是 `lerp(prev, cur, partialTick)`。它有一个**没写出来、但必须成立**的前提：

> `prev ← cur; cur ← 新值` 这次交换**恰好发生在 tick 边界**（partialTick = 0）。

只有那样，两段折线才首尾相接：

```
交换前 φ→1：lerp = P(t)
交换后 φ=0 ：lerp = P(t)      ← 接上了
```

而现实里，**数据是按"拍"到的、帧是在任意相位渲染的**，于是交换落在一个任意相位 φ₀：

```
交换前：P(t−1) + φ₀·Δ
交换后：P(t)   + φ₀·Δ = 交换前 + Δ        ← 每个采样周期凭空跳一整个 Δ
```

注意跳变幅度 = **Δ**（与 φ₀ 无关）⇒ 表现就是"动一下 → 停一下 → 又跳一下"。**采样越稀，Δ 越大，越难看。**

### 1.1 这个类已经害过我们两次

| 时间 | 症状 | Δ 有多大 | 修法 |
|---|---|---|---|
| 2026-09-25 | 天体移动"还是不丝滑" | 地球每 tick **108 km** ⇒ 站在 2.2R 处看 ≈ **6.9 像素**（而顺滑运动每帧才 2.3 像素） | `CelestialBody` 改成**带时间戳的快照环 + 渲染延迟** |
| 2026-10-02 | 牵引枪**线抽抽、框也抽抽** | 端点是服务端广播来的，`BROADCAST_INTERVAL_TICKS = 2` ⇒ **10Hz**，而插值窗口只有 1 tick | 抽成通用件 `TimedSamples`，牵引枪接上 |

**牵引枪那两条症状是同一个源**：框的中心就是同一个 `renderEnd` 的输出——
```java
b.renderEnd(partialTick, E);        // 画线用它
...
lockCenter = E;                     // 框也用它
```
所以以前"分开修线、分开修框"必然修不好：它们是同一个数。

## 二、通用件

### 2.1 `com.mss.polymech.util.TimedSamples`

把 `CelestialBody` 里那份**已验证过**的机制抽出来（本项目硬规矩：同一概念不许有两份实现）：

- 每拍 `push(value...)` 打一个 `System.nanoTime()` 时间戳；
- 渲染取 `渲染时刻 = 现在 − 延迟`，在**包住这个时刻的相邻两拍**之间插值；
- **越过最新样本一律夹住，绝不外推**（外推会在丢包时把物体甩到屏幕外）；
- 同一拍去重窗口 4 ms（上游一次逻辑更新可能分几次调用）；
- 四元数走 **slerp + 最短弧**（分量线性插值在四元数上是错的；短弧不做会绕一大圈
  —— 本项目在牵引枪角伺服上栽过同一个坑）。

### 2.2 ★ 延迟必须"由发包间隔推出"，不能照抄

这是本次最容易踩的坑，也是把关系写成**式子**而不是注释的原因：

```java
// PhysgunClientState
private static final double INTERP_DELAY_SECONDS =
        2.0 * PhysgunBeamPacket.BROADCAST_INTERVAL_TICKS / 20.0;
```

延迟必须 **≥ 2 × 采样周期**，"渲染时刻永远被两拍包住"才成立：

| 场景 | 采样节奏 | 默认 0.10 s 够吗 |
|---|---|---|
| 天体 | **每帧**推进（100+ Hz） | 够，余量好几拍 |
| 牵引枪（原 `INTERVAL=2`） | 每 2 tick = **0.1 s** | **不够**：延迟刚好 = 1 个周期 ⇒ 网络稍抖就越过最新样本、被夹住不动 ⇒ **又开始抽** |

所以同时把发包间隔也改了：

```java
// PhysgunBeamPacket
public static final int BROADCAST_INTERVAL_TICKS = 1;   // 原 2
```

两个理由：① 采样越稀每拍跳变越大；② 它决定渲染延迟 —— 间隔 0.05 s ⇒ 延迟 0.10 s，
**与天空那条线取的是同一个数**（`CelestialBody.INTERP_DELAY_SECONDS = 0.10`）。

## 三、用到了哪里

| 渲染量 | 之前 | 现在 |
|---|---|---|
| 光束**起点** | `lerp(prevStart, start, partialTick)` | `startSamples.evaluate` |
| 光束**终点** ← 线 + 框的共同来源 | `lerp(prevEnd, end, partialTick)` | `endSamples.evaluate` |
| **虚拟竿尖**（受力弯曲） | `lerp(tipPrev, tip, partialTick)` | `tipSamples.evaluate` |
| 抓取框/悬停框的体位姿（**主**路径） | `poseOf` → `ClientPhysics.liveTransform` | **本来就平滑**（100Hz 本地刚体状态），无需改 |
| 抓取框/悬停框的体位姿（**兜底**路径） | `poseOf` → `ClientBody.renderX/renderRotation(partialTick)` | **已接**：`ClientBody` 加了四条快照环（`phys*` 客户端刚体自己 / `net*` 服务端同步），`renderX/Y/Z` 与 `renderRotation` 都先走时间戳插值、样本不足才退回旧 lerp |
| 落点标记 | 本地每帧算（眼+视线×距离） | 本来就平滑，无需改 |

> **为什么兜底路径也要接**：`ClientBody.renderX/renderRotation` 的两个分支（`physValid` / 网络）
> 都是"按拍更新、按帧渲染"，就是同一类。它们不只服务牵引枪 ——
> `PhysicsBodyRenderer` 画**所有**物理体也走这里，所以这条修的是"所有物理体的渲染平滑度"。
> 延迟取 0.10 s 对两种上游节奏都成立（上游更快时是"好几拍"、正好 20Hz 时是"两拍"）。

三处都保留**旧的 `lerp` 作为回退**：样本不足（刚抓上，还没攒够两拍）时最多抽一两拍，
而不是因为样本没攒够就整条光束不动。

## 四、判据（程序判定，不让用户肉眼说"好像不抽了"）

### 4.1 游戏内：`[牵引枪·丝滑判据]`

`com.mss.polymech.util.FrameJitterMeter`（同为通用件）在渲染时逐帧喂**光束终点 E**，
窗口 120 帧；**松手那一刻**打一行（照 `[牵引枪·旋转判据]` 的做法，不刷屏）：

```
[牵引枪·丝滑判据] 120 帧：每帧位移 均=0.0412 最大=0.0455 最小=0.0370 格；
    抖动(最大/均)=1.10（阈值 1.50）；跳变帧=0/120 ⇒ PASS
```

口径与天空那条线的"太空顺滑"**完全一致**（每帧位移 均/最大/最小、抖动=最大/均、跳变帧=位移<5%均值）。

⚠️ **均值≈0 时判"不可判"而不是 PASS**：物体本来就没动（例如抓着一个躺在地上的体），
"没动"与"动得丝滑"是两件事 —— 判 PASS 就是一条永远通过的**假判据**（本项目栽过"死判据"）。

### 4.2 实机判据表（绝对坐标；程序判定 PASS/FAIL）

| # | 操作 | 判据 | 期望 |
|---|---|---|---|
| S1 | 抓一个物体，**横向走动** 1~2 秒后松手 | 聊天栏出现 `[牵引枪·丝滑判据]` | PASS = 抖动 ≤ 1.50 且 **跳变帧 = 0** |
| S2 | 抓一个物体，**原地快速甩视角** 1~2 秒后松手 | 同上 | PASS = 抖动 ≤ 1.50 且 跳变帧 = 0（甩视角时 Δ 最大，最容易暴露） |
| S3 | 抓着一个**正在飞的**物体（推进/爆炸后） | 同上 | PASS = 抖动 ≤ 1.50；这条的 Δ 最大，是三条里最严的 |
| S4 | 抓着物体**转它**（TAB + 鼠标） | 线跟着转、框**不跳格** | PASS = 框始终套在同一格上，不来回蹦 |
| S5 | 抓一个**静止**的物体不动，然后松手 | 读数应说"静默样本…不可判" | PASS = **不出现 PASS**（这条验的是判据本身不是死的） |

### 4.3 离线：第 19 步 `InterpSmoothnessProbe`（6/6，已落地）

**调的是生产代码本体**（`TimedSamples` / `FrameJitterMeter`），不是复刻一份公式 ——
本项目栽过"探针复刻的契约与真实现不一致"。时钟由 `TimedSamples` 的**可注入构造器**给定，
所以"任意相位"是**确定性**的（靠 `Thread.sleep` 造相位不行：Windows 粒度约 15ms，而一个 tick 才 50ms）。

仿真：200fps 渲染 + 20Hz 采样（= 改完后的 `BROADCAST_INTERVAL_TICKS = 1`）+ 延迟 2 个采样周期 + 匀速 8 格/秒。

| 组 | 场景 | 实测 | 结论 |
|---|---|---|---|
| **A** | **固定相位**（交换正好在 tick 边界）+ 旧 lerp | 均=0.0400 最大=0.0400 抖动=**1.00** | PASS —— 证明**量具本身能给出 PASS** |
| **B** | ★ **任意相位**（半个采样周期）+ 旧 lerp | 均=0.1120 最小=0.0400 最大=0.4400 抖动=**3.93** | **如期 FAIL** —— 判据不是死的，这就是"抽抽"的量化 |
| **C** | 同样的任意相位 + `TimedSamples` | 均=0.0400 最大=0.0400 抖动=**1.00** | PASS —— 修好了 |
| **D** | 连续丢 4 拍 + `TimedSamples` | 最大越界 **0.000000e+00** 格；丢包后仍在插值 | PASS —— **夹住，不外推**，也没被冻死 |

★ **没有 A 与 B，C 的 PASS 就是死判据**：A 证明量具能通过、B 证明量具能失败。

**B 组暴露的"抽"是锯齿，不是停顿**：每帧位移最小 0.04（= 一帧的真实位移）、最大 0.44（≈ 11 帧的量）。
机理是旧写法在交换那一刻**倒退**到新一拍的值（本次探针里那一段的 partial 从 0.9 掉回 0），
所以 `跳变帧`（位移 < 5% 均值）为 0 而 `抖动`=3.93 —— **判这个毛病要看抖动，不是看跳变帧**；
`跳变帧` 抓的是另一种失效（夹住后冻死）。

⚠️ **本探针第一版把自己判 FAIL 过一次，原因是判据写错**：用 `simTime % samplePeriod` 算 `partialTick`，
浮点取模在 tick 边界给出 `0.0499999` 而不是 `0`，于是 `partialTick≈1` 下一帧又跳回 `0.1`，
**凭空造出一个倒退跳变**（A 组因此冤枉地抖动 4.15）。改成整数帧运算后 A 组 = 1.00。
教训与 §5.3（`-q90`）、`BodyLocalMappingProbe` C 组同源：**期望写错时先怀疑判据，不要先怀疑代码**。
已用契约钉住那个整数写法。

### 4.4 天体那份私有实现已收口（第 20 步 `CelestialSmoothProbe`）

机制抽出来之后，`CelestialBody` 里那份**私有实现**（`histT/histP/histR` + `locate`）必须改为委托 ——
否则"同一概念两份实现"迟早漂移（本项目硬规矩）。

但那是**已经验收过的天空那条线**，而此前**没有任何离线探针覆盖它**：改完只能靠人去游戏里
看天空有没有变卡，那正是用户明确说过不想反复做的事。所以顺序是**先钉住、再重构**：

| | 抖动 | 每帧位移 | 不外推 | 单位四元数 | 转角步长 |
|---|---|---|---|---|---|
| **重构前** | 1.00 | 0.1500 | 47.8499 ≤ 50.2500 | 4.44e-16 | 0.00508 |
| **重构后** | 1.01 | **0.1500** | 47.8495 ≤ 50.2500 | 2.22e-16 | 0.00506 |

差异只在末位，且来自探针用**忙等**推进真实时间（类内部时钟是 `System.nanoTime()`，
**没有**可注入时钟 ⇒ 不能用 `sleep`：Windows 粒度约 15ms，而一帧才 5ms）。
**每帧位移 0.1500 完全一致** = 速度没被拉慢/加快，这是"行为没变"最硬的一条。

探针的 5 条判据：① 平滑（抖动 ≤ 1.5 且 跳变帧 = 0）② 每帧位移量级（期待 速度/帧率）
③ 不外推 ④ 姿态恒为单位四元数 ⑤ 转角步长有界（最短弧没坏）。

**唯一有意保留的语义差异**：原来位置与姿态被绑成**同一拍**（两条环共用一个时间戳），
现在各一条环、各按自己的节奏插值 —— 姿态更新稀疏时不会再被位置拖着走。语义上更准。

收口后 `TimedSamples` 是全项目**唯一**一份"带时间戳的插值"实现，使用方：
`PhysgunClientState`（3 条环）、`ClientPhysicsWorld.ClientBody`（4 条环）、`CelestialBody`（2 条环）。

1. `.\gradlew compileJava --console=plain` 必须 `BUILD SUCCESSFUL`。
2. `.\native\jni-smoketest\run-offline-checks.ps1` 必须 **20/20 步、exit 0**。
3. **任何**"按拍同步、按帧渲染"的新量都必须走 `TimedSamples`，不许再写
   `lerp(prev, cur, partialTick)` —— 契约钉住了 `PhysgunClientState` 里那一处；
   新增同类渲染量时请照抄它的接法（谁写数据谁 `push`，读的时候 `evaluate`）。
4. **延迟必须由采样周期推出**：新增一处时先问"这个量多久来一拍"，
   然后 `delay = 2 × 周期`。契约钉的就是这条式子（`2.0 * BROADCAST_INTERVAL_TICKS / 20.0`）。
5. 改了发包间隔 ⇒ 延迟自动跟着变，但**采样越稀越难看**，别为了省包把它调大。
6. 助手不启动客户端；实机由用户验。

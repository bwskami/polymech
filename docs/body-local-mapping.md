# 体局部格 ⇄ 世界格映射（牵引枪遗留缺口 2）

> 权威记录。修的是「物理体被转过/挪过之后，在它旁边放方块会吸错格」这个缺陷。
> 离线判据：`native/jni-smoketest/BodyLocalMappingProbe.java`（第 **17** 步，16 条）。

---

## 一、缺陷是什么

`PhysicsBodyTracker` 里有两处把「体局部格」与「世界格」互相换算，原来都是**轴对齐**的：

```java
// findAdjacentBody：局部格 → 世界格
int wx = tracked.origin.getX() + e.dx();
int wy = tracked.origin.getY() + e.dy();
int wz = tracked.origin.getZ() + e.dz();

// placeBlockAt：世界格 → 局部格
int dx = pos.getX() - tracked.origin.getX();
```

而 `origin` 是**建体时**那块区域的最小角，`withTransform` **从不更新它**。所以错两层：

1. **体被牵引枪转过之后全错** —— 方块的真实世界位置不再是 `origin + 局部`；
2. **体只是被推着平移过也一样错** —— `origin` 是冻结的，体挪走了它指的还是老地方。

症状（用户可见）：**在转过或挪过的物理体旁边放方块，要么吸不上去，要么吸进错误的格子。**

> 注意：同一族的 `localToWorld` 反而是**对的** —— 它用的是
> `bodyPos + R·(局部+0.5)`，一直含旋转。所以缺陷不是"整个类都错了"，
> 而是"有两处自己算了一份轴对齐的映射"。**同一个概念两份实现**正是本项目的旧伤
> （见 `mps-clone-plan.md` §29.3），这次一并收敛掉。

---

## 二、怎么修的

**判据改在体局部空间做**：把世界格变换到体局部，再与方块列表比曼哈顿距离。

```java
RayBox.toLocalCell(bodyPos, rot, pos.getX(), pos.getY(), pos.getZ(), cell);   // 世界格 → 局部格
int manhattan = Math.abs(e.dx() - cell[0]) + Math.abs(e.dy() - cell[1]) + Math.abs(e.dz() - cell[2]);
```

**为什么必须在局部空间判**：局部空间里方块永远是**轴对齐整数格**，曼哈顿距离在那里才良定义。
体一旦斜过来，世界空间里根本没有"面相邻的世界格"这回事。

**单一来源**：新映射提在 `RayBox`（纯函数、零 MC 依赖）里，`PhysicsBodyTracker` 与
客户端拾取（`RayBox.toLocalPoint`）共用同一对：

| 方法 | 方向 | 式子 |
|---|---|---|
| `RayBox.toLocalCell` | 世界格 → 局部格 | `floor(R⁻¹·(p + 0.5 − bodyPos))` |
| `RayBox.toWorldCenter` | 局部格 → 世界格心 | `bodyPos + R·(局部 + 0.5)` |
| `RayBox.toLocalPoint` | 世界点 → 局部点 | `R⁻¹·(p − bodyPos)`（原有） |

`PhysicsBodyTracker.localToWorld` 现在也走 `RayBox.toWorldCenter`（行为不变，去掉重复实现）。

## 三、★ 一个必须讲清楚的边界：斜轴旋转下"整数格往返"不可能恒等

写这个探针时我第一版把判据写成"**所有**旋转下局部→世界→局部必须回到原格"，
结果斜轴那两组失败了 —— **是判据写错，不是代码错**（与 `physgun-rotation.md` §5.3 同一类）。

原因：`floor(世界心)` 把连续世界点**吸附到世界整数格**。轴对齐旋转（90° 的整数倍）
把整数点阵映到自身，所以两个格心重合、往返精确；**斜轴**下局部点阵与世界点阵本来就错位，
两个格心最大相距 `0.5·√3`，反算最多落到相邻格 —— 这是**网格量化的固有极限**，任何方案都躲不掉。

所以判据分成三层（探针 C 组）：

| 层 | 断言 | 适用 |
|---|---|---|
| C1 | 实值逆变换**精确**（`toLocalPoint(toWorldCenter(x)) == x + 0.5`） | **所有**旋转 |
| C2 | 整数格往返**精确** | 90° 整数倍（格对齐） |
| C3 | 整数格往返误差**有界 ≤1 格** | 斜轴（量化极限，**不是缺陷**） |

**对照**（探针 C4）：同一场景下**旧**映射的最大偏差是 **11 格**，而且随体位移增长 ——
是**无界**的。新映射 ≤1 格。所以修复对两种情况都严格更好。

## 四、行为中性（A 组，最重要的一条）

**恒等旋转 + 体未移动时，新映射与旧映射逐位一致**（343 个格，最大差 `0.000e+00`）。

这条证明本次修复**没有顺手改语义**：没被转过也没被挪过的体，放方块的行为与修复前完全相同。
（与 space 0.3.0 对齐时那条"`rotate=0` ⇒ 行为中性"是同一个思路。）

## 五、实机判据表（用户验收用）

前提：进游戏，太空里造一个 **3 格长**的物理体（比如沿 X 摆 3 块石头），手上有牵引枪和石头。

| # | 操作（绝对、可复现） | 期望 | 判定方式 |
|---|---|---|---|
| 1 | **不转也不挪**，直接贴着它的一端放一块石头 | 被吸进体里（连成 4 格），**不是**在旁边生成一个新体 | 看它是否跟着体一起动（推一下体，新块跟着走） |
| 2 | 用牵引枪把它**绕 Y 转 90°**，松手，再贴着它的"新端面"放一块石头 | 被吸进体里，且新块长在**转动后**的那一端 | 推一下体，新块跟着走；且新块位置与转动后的朝向一致 |
| 3 | 用牵引枪把它**平移 10 格**（按住右键往前拖），松手，再贴着它放一块石头 | 被吸进体里 | 同上 |
| 4 | 用牵引枪把它**斜着转一个角度**（不是 90° 的整数倍），再贴着放一块石头 | 能吸上（可能差一格，见 §三），**不会**在十几格外凭空生成新体 | 同上 |
| 5 | 在**离体 2 格以外**放石头 | 生成**独立**的新物理体（不吸附） | 新块不动体、体不动新块 |

**为什么这张表不用"程序判定 PASS/FAIL"**：缺口 (1)（旋转控制）能在服务端算残角，
是因为"目标朝向"是个绝对量；而"方块该被吸到哪个格"在斜轴下**本身就是模糊的**
（§三的量化极限），没有一个诚实的程序判据能把它判成 PASS/FAIL。
所以这里给的是**可复现的操作 + 可观察的后果**（新块跟不跟着体走），
而不是假装有一个精确判据。判据 1/2/3 是精确的（格对齐），4 是"不灾难"级别的。

**已知会在实机上看到的非缺陷现象**：
- 判据 4（斜轴）偶尔差一格 —— 见 §三，量化极限。
- 体被转成**斜的**之后，"面相邻"在视觉上会有歧义（方块的边对着世界格）—— 同上。

## 六、验证约定

1. `.\gradlew compileJava --console=plain` 必须打印 `BUILD SUCCESSFUL`。
2. `.\native\jni-smoketest\run-offline-checks.ps1` 必须 **17/17 步、exit 0**（本项加了第 17 步）。
3. 改了 `RayBox.toLocalCell` / `toWorldCenter` 的式子 ⇒ 必须同步 `check-artifact.ps1` 的契约
   与 `BodyLocalMappingProbe`（它直接调真实现，不是复刻）。
4. ★ `check-artifact.ps1` 有一条 **mustNot** 契约钉住旧映射
   （`tracked.origin.getX() + e.dx()`）不得回归 —— 删除类改动只能这样钉。
5. `run-offline-checks.ps1` 需**双** BOM（`EF BB BF EF BB BF`）、
   `check-artifact.ps1` 需**单** BOM（`EF BB BF`）—— `edit`/`write` 工具会剥 BOM，
   改完要用 `[System.IO.File]::ReadAllBytes`/`WriteAllBytes` 字节级补回。
6. 本 shell 是 **Windows PowerShell 5.1**（没有 `pwsh`）。
7. 助手不启动客户端；实机由用户验。
